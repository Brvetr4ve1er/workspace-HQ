# Personal roadmap: one assistant where the owner already is

**Date:** 2026-11-07 · **Lane:** frontend (structure-lane asks are marked) · **Status:** the owner approved cooking batch 1 on 2026-11-07, once this plan was ready.

**What it answers.** The owner asked for the plan to focus on the features they personally want and need, to cover their other projects (finance hq, retrogallery, omnidownloader), and to aim for one global agentic assistant that runs on the phone, the PC, a VPS and the browser.

**Decided by the owner while it was planned (2026-11-07):**
- "finance hq" is the Money space (key 9): this plan deepens Money instead of adding another app.
- Cosmos (retrogallery) takes key 0, as its own track.
- One browser extension for everything: the WorkspaceHQ Bridge.
- No VPS yet: nothing here needs one, and the phone path works without it.
- A client delivery view, as its own track.

**Defaults in force until the owner answers the three before-cooking questions** (see "Open questions"): the Cosmos step is committed on a local branch, `hold/cosmos-core`, that is never pushed; "Find the best version" ships as a viewer (no downloads); standing Brief items keep their slots (the "+N more" line ships either way).

**How it was made.** Five read-only recon dossiers (the owner's needs, Cosmos, omnidownloader, finance, the assistant's reach), four rival plans (assistant-first, ports-first, daily-loop, skeptic), three judges (owner fit, architecture, constraints and safety), a synthesis, two critics (completeness and a batch-1 red team) and a final pass. The evidence behind it (personal counts, the owner's own words, the needs dossier) stays local in `docs/audits/`, which is never committed.

**Batch 1's cook specs:** [`docs/superpowers/plans/2026-11-07-kitchen-batch1.md`](../plans/2026-11-07-kitchen-batch1.md).

## North star

Wherever the owner already is (the tray, Home, any Claude session including on the phone, the browser toolbar), WorkspaceHQ answers from measured local data: what needs me, where did each Claude session stop, have I solved this before, how far along is each client job, what did I spend. Every assistant action passes one rulebook and lands in one log, and every surface counts its own use. Nothing needs an LLM to be true, nothing leaves this PC without the owner's click, and nothing needs a VPS.

The owner's day runs through Claude Code sessions in about 24 folders (119 indexed chats, active 22 of the last 30 days), the browser (380 focus events in 4 days), GitHub and Vercel, and a PC that sleeps a lot. It almost never runs through the WorkspaceHQ window: about 10 relaunches in 26 days, and 0 calls to hq_brief since it shipped. So this plan builds no new rooms. One deterministic brain in the always-on tray app answers from measured local data, and thin surfaces carry the answers to where the owner already is: the tray, Home, every Claude session (the phone included, through Remote Control, with no VPS) and the one browser extension. Three spine pieces make it one assistant instead of five half-tools: - one screen-safe projection of the Brief (rule wording, counts and opaque refs), the only text allowed off the main window; - one rulebook for every tool call (read, note, run, stage; hourly limits; one names-only log); - one usage counter (hq:use) that every new surface reports to. The logs hold 0 'use' events today, so this is what lets each next batch be chosen by measured use. That is the 2026-10-28 audit's rule: a feature is done when its data file grows. The owner's other projects come in as committed tracks. Each starts with the step whose failure would hurt most: - 'finance hq' is the Money space. Money has had zero entries since 2026-11-03, so the first step removes setup (a one-minute start card) and makes a spend a five-second line. - Cosmos takes key 0. The first step pins image ids that must never move and keeps data/cosmos/ out of the public repo; it stays on a local branch until the owner says the ported code may be public. The engine and the Feed then land together in batch 2. - omnidownloader's image half becomes the extension's 'Find the best version'. Nothing is downloaded unless the owner says yes; the video helper stays behind its installs, in its own repo. - The client delivery view shows what's left against an owner-written scope (or a checklist file the owner picks), the newest preview link, and an update to paste to the client. The visual centrepiece is a live board of every Claude session, with Codex folded in: where each one stopped, how many usage-limit stops hit this week, and one-click Resume.

## Architecture: one brain, thin surfaces

One deterministic brain: WorkspaceHQ's Electron main process. It is already always on (hidden autostart at login, the tray, a 15-minute heartbeat), but only while the PC is awake: 48 suspends in the 10 days to 2026-11-07. So every surface states how old its answer is. Senses: - the nightly scan (data/latest.json), pc-health.json, github.json, accounts.json; - the Claude Hub index of every Claude Code session (data/claude/hub.sqlite, 137 MB, live through fs.watch plus a 60 s sweep; 47 of its 119 chats exist nowhere else, because Claude Code deletes transcripts after 30 days); - Codex's session index (~/.codex/session_index.jsonl: titles and times only); - browser focus from the Bridge, the money view, the app's own power log; - later, the Cosmos library and the owner's client scope files. Engines (pure, no LLM): - brief-core: rules, at most 3 items, change-only toasts; gains six senses, an overflow list and a count field; - sessions-core: how each Claude session ended, including Claude Code's four usage-limit notices; - quicklog: a typed spend line becomes a money intent; - delivery-core: checklist parsing, the preview-link pick, the update text; - later, Cosmos's sticky ids and search grammar. Spine: - dashboard/brief-project.mjs is the only projection any surface outside the main window may show: rule wording, counts, opaque refs and a nav of {kind, tab, sub}. Never names, amounts, paths or project ids; main maps a ref back to its item. - dashboard/assist-core.mjs plus mcp/workspacehq/guard.mjs is the rulebook. Every tool has a tier (read, note, run, stage). No remote door gets an act tier. Hourly limits are counted from one file, because every Claude session runs its own MCP process. - data/assistant-audit.jsonl is the one names-only log of tool and bridge calls; hq:use writes 'use' events for app surfaces into the existing day log (logs/app-*.log). - data/.refresh.lock is the one lock the app's scan and a session's raw collector pass share. Claude (desktop Code tab, CLI, the phone through Remote Control) is the optional talking layer over the same brain, through the project's workspacehq MCP tools. The local model stays optional and is not running on this PC (neither :11434 nor :1234 answers). An LLM only ever runs on the owner's click.

**Safety.** Assume a hostile network and hostile content. What leaves the main window: - One projection (dashboard/brief-project.mjs) is the only text the tray, the toolbar and any later phone door may show: rule wording, counts, opaque refs and a {kind, tab, sub} nav. - It never carries project ids, project, quest or bill names, amounts, paths or page titles. The tray only opens it. Sessions the app opens: - Resume from the board always passes --permission-mode default, because the owner's global default is auto (~/.claude/settings.json). Phone-continuable launches are always default. - A Claude session opens only on the owner's click. Ids and paths travel by environment variable, never on a command line. Recall: - It reads only what the owner and Claude wrote: never the 39,700 tool rows, subagent turns, forgotten chats, or Instagram/Facebook rows, and claude.ai rows only when asked. - By default it reads only chats from the session's own folder, so a session in one client's repo can't read another client's chats unless it asks for all. - It masks every string again on the way out (a snippet whose mask changed loses its highlights, never the mask) and frames it as data, never instructions. - It says plainly that raw text stays in the search index.

Seven small dishes make what already exists reach the owner (the Brief at the start of every Claude session, a quiet lane, a phone file, a real test notification), get measured (act marks and a counts-only use report), stay safe (a chat-index snapshot outside the repo, quiet and light defaults) and cost less to change (one gate command, a settle-based button sweep). (b) THE NIGHTLY TAKES data/.refresh.lock the way dashboard/refresh-lock.js does. Exact lock shape (read from that file): JSON {pid:int, by:string, startedAt:ISO}, created with flag wx (CreateNew); a lock is STALE when its pid is gone OR it is 15 minutes old or older (also a startedAt more than 60 s in the future, and an empty or unparsable file is 'fresh' for 5 s then stale); a stale lock is reclaimed under a short-lived data/.refresh.lock.reclaim gate file created wx (10 s ceiling), looked at again inside, never replaced if fresh by then; release only removes a lock whose by matches (and pid when given). refresh-lock.js HOLDERS is ['app','mcp'] and an unknown by is read as a torn file, so the nightly needs a third holder: the fe: commit adds 'nightly' to HOLDERS and a refusalText line ('the nightly scan is running - try again in a few minutes') with tests. The PowerShell side lives in a NEW tools/nightly-lock.ps1 (functions Take-NightlyLock / Heartbeat-NightlyLock / Release-NightlyLock, dot-sourced), so run-pipeline.ps1 changes by about six lines in ONE struct: commit.

CHILD-OF-HOLDER RULE (critic finding, verified): the app's Scan and its post-commit rescan take the 'app' lock and THEN spawn run-pipeline.ps1 as a direct child (dashboard/main.js:329 take, :335 spawn). A pipeline that skipped on any fresh lock would skip every in-app Scan. So Take-NightlyLock first reads the lock; when it is fresh, by is 'app', and the lock's pid equals this PowerShell's own parent pid or one of its next two ancestors (Get-CimInstance Win32_Process ParentProcessId, three hops at most), the run is the app's own child: it proceeds as 'inherited', writes nothing, heartbeats nothing and releases nothing (the app owns and releases that lock). No main.js edit and no environment variable are needed. Any other fresh holder (the app's lock with a different pid, 'mcp', 'nightly') is a real collision.

COLLISION BEHAVIOUR (critic finding): a bare exit 0 would drop the whole nightly run with no retry and the data would go a day stale. Take-NightlyLock therefore polls every 15 s for up to 10 minutes (override with env HQ_NIGHTLY_LOCK_WAIT_S, which the tests set to 1; no new param on run-pipeline.ps1) and only then logs ONE line 'skipped: refresh lock held by <by> since <time>' and exits 0 (no error). Heartbeat: after each step the run rewrites startedAt in its own lock (same shape; a one-line CONTRACT note) so the 15 minute ceiling never drops a lock under a slow enrich; release is in a finally that also runs on 'exit $code' paths (a test proves release on a non-zero exit, and if finally does not cover exit in this PowerShell the release moves to a wrapper function; the test decides). Fail open like the JS: a lock the disk will not take never blocks the run.
